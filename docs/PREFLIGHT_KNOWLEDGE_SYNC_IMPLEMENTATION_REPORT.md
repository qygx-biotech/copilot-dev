# Preflight knowledge synchronization — implementation report

Implemented on 2026-09-06. The architecture and lifecycle diagram are in [PREFLIGHT_KNOWLEDGE_SYNC_PIPELINE.md](PREFLIGHT_KNOWLEDGE_SYNC_PIPELINE.md). Source files mentioned below are relative to the repository root.

1. **Branch and working tree.** Created `feature/preflight-knowledge-sync-agent` from `feature/open-semantic-intent-ir`. Existing uncommitted work was preserved. No reset, clean, commit, push or deployment was performed.

2. **Files changed by this implementation.** New files: `docs/request-pipeline.js`, `alibaba-fc/test/preflight-knowledge-sync.test.js`, `alibaba-fc/test/helpers/preflight-fixture.js`, `scripts/benchmark-preflight-sync.mjs`, `docs/benchmarks/preflight-knowledge-sync.json`, the architecture document and this report. Regression expectations and coverage changed in `alibaba-fc/test/local-workspace.test.js`, `alibaba-fc/test/source-system.test.js`, `alibaba-fc/test/retrieval-profiles.test.js`, `alibaba-fc/test/workspace-side-chat.test.js` and `desktop/test/project-filesystem.test.mjs`. Existing architecture documents were updated. Some of these files already had changes when work began; the full Git diff therefore includes earlier work. The pre-existing changes to `alibaba-fc/Archive.zip`, `alibaba-fc/test/cloud-retrieval.test.js`, `alibaba-fc/test/oss-pdf-review.test.js` and `desktop/test/side-chat-fixture/scenarios.js` were retained, not created by this implementation.

3. **Previous request pipeline.** Side Chat performed its own source/catalog refresh before context construction. Source preparation, card creation and freshness checks were also available later through retrieval and corpus preparation. Agent Command did not have the same mandatory shared synchronization gate. Profile and language heuristics influenced context routing before a shared L0–L3 readiness boundary existed.

4. **New request pipeline.** Both surfaces enter `ProjectContextService.buildContext()`, await the shared `AgentRequestPipeline.preflight()`, then interpret the current request, construct an evidence-needs plan, retrieve bounded evidence and invoke the existing FC main-agent loop. Preflight performs metadata reconciliation, lazy dirty-source verification and any required maintenance. An unchanged synchronized workspace proceeds immediately. The main agent retains the conversation, goal, tool selection, scientific reasoning and final answer.

5. **Source reconciliation.** The existing registry compares a single directory-tree snapshot against known sources. It uses relative path, kind, size, timestamp, filesystem identity and registry status. Native Electron stat now supplies JSON-safe nanosecond timestamps and device/inode identity. The scan does not parse files, calculate content hashes, update QMD or call a model. Unchanged registry/catalog state is not rewritten.

6. **Added, removed and modified detection.** Reconciliation returns deterministic `added`, `removed`, `possiblyModified` and `unchanged` fields. A missing old path is a deletion; a new path is an addition unless filesystem identity safely establishes a rename. Identity matching does not merge distinct hard links. Changed stat signatures produce `possiblyModified`. Persisted pending and partial work is retried even if a subsequent scan sees no new metadata change. Missing sources retain historical tombstones but leave active registry results and paper selections.

7. **Hash behavior.** Only sources that need preparation or have dirty metadata are read and hashed. Existing harness content hashes remain authoritative. Same-hash timestamp changes update stat state and reuse L1/L2/L3, including legacy prepared projects without the new sync marker. Same-content renames refresh path provenance using cached content/cards. A new hash invalidates only that source's active artifacts and affected downstream state before rebuilding. Deletion requires no hash. A metadata-only scan cannot discover an in-place replacement that preserves every observed stat field; explicit verification or a subsequent metadata change is needed.

8. **KnowledgeSyncAgent.** This is a bounded maintenance orchestrator with a frozen callback allowlist, not a conversational model loop. Input is workspace ID, changed source IDs and the fixed synchronization task. Capabilities cover readiness, cards, topics, experiments, documents, removal, readiness persistence and metadata refresh. It receives no user question or conversation and exposes no shell, arbitrary tool dispatcher or recommendation writer. The job manager records one shared `knowledge-sync` job.

9. **Paper L1.** The worker first obtains a stable source version, then invokes existing local PDF extraction, parsed pages/chunks, page-preserving evidence Markdown and incremental lexical QMD indexing. Source IDs, hashes, page references and existing evidence handles remain attached. No LLM is introduced for extraction. A valid L1 remains usable if a later card/topic stage fails.

10. **Paper Card L2.** After L1 is ready, the worker calls the existing canonical Paper Card preparation capability. Existing validation, structured JSON, Markdown mirror and source/hash/model/prompt cache identity remain in use. Genuine content changes rebuild the affected card. The existing Electron → Alibaba FC → Requesty pathway performs provider work. Cards provide reusable routing/summary knowledge; scientific claims still require original/L1 evidence.

11. **Topics L3.** Topic updates happen after a valid card and are serialized. Structured entities, topics and clear engineering methods drive deterministic assignment. Membership records retain the source version. Changed memberships mark affected summaries and shallow ancestors stale; stale summaries are excluded from active topic Markdown. No global hierarchy rebuild, bulk summary regeneration or new topic-classification model call is added. Existing request-driven summary policy remains available.

12. **Experiment and other data behavior.** Experiments reuse existing XLSX/XLS/CSV/TSV/TXT parsing, deterministic header/unit aliases, canonical schema records and searchable descriptors. Chinese headers, original cells, units, sheet names and source provenance remain available; the original workbook is unchanged. The existing bounded FC schema mapper handles unresolved mappings and preserves its cache. Numerical ranking/filtering uses structured experiment tools. Experiments receive no Paper Cards. Protocols and generic supported text/PDF sources receive source-specific original-language L1 in the project-memory collection. Unsupported binary protocol formats produce an explicit partial status. The handler table in the architecture document lists discovery scope and formats.

13. **Deletion behavior.** Deleted papers lose active parsed evidence, L1 Markdown, canonical/cache card associations and files, L2 Markdown, L3 memberships and active selection. Affected synthesis/workflow artifacts become stale while historical provenance remains. Deleted experiment artifacts and descriptors disappear from active queries. Source-derived memory associations are invalidated. QMD is updated; if that update fails, affected collections are suppressed from search until repair and cleanup remains pending. A source that disappears during preparation is cleaned in the same request without another directory scan.

14. **Deduplication and concurrency.** Both surfaces share one pipeline per source system. Concurrent requests await the same in-flight reconciliation/sync promise. Turn IDs reuse that result through card/catalog work; an explicit host filesystem mutation can invalidate the snapshot. The worker pool is limited to two sources, uses existing per-source preparation locks and the project QMD queue, serializes topic mutations and queues registry persistence. Partial stages are persisted and reused on retry. Cancelling one consumer does not cancel another; changing projects aborts the project-lifetime work and rejects writes against a changed workspace identity.

15. **Compact result schema.** The report contains `status`, `added` and `removed` counts by source kind, `updated` layer counts, `failures: [{sourceId, stage, code, retryable}]`, and `sources: [{sourceId, status, contentHash}]`. Successful stage counts describe completed work. FC allowlists fields and bounds arrays. Raw chunks, full cards, model prompts/responses and maintenance transcripts are not copied into the main context. Partial coverage is explicitly communicated; the main agent can use ready sources and existing bounded fallback or explain the missing coverage.

16. **Language policy.** The handoff retains `originalQuery`, `canonicalQueryEn`, `inputLanguage` and `answerLanguage`. A current explicit answer-language instruction takes precedence; otherwise the input language supplies the default, with existing explicitly saved language preferences retained. The app's UI language no longer inserts a conflicting answer instruction. Raw sources and scientific identifiers remain unchanged.

17. **Chinese interpretation and default policy.** When local interpretation is insufficient, one existing authenticated FC semantic call supplies a canonical English goal, entities, operations and constraints together. There are no separate translation, entity and intent calls. Retrieval retains both the original and canonical query. Chinese characters alone no longer trigger Deep. Stored Light/Medium/High settings remain compatible, but the shared pipeline resolves them all to the existing Medium local-first policy with evidence-driven escalation. The main answer follows `answerLanguage`.

18. **Evidence-needs planning.** `planEvidenceNeeds()` composes registered semantic objects and operations into an advisory plan after synchronization and interpretation. Exact paper facts use L1/direct tools; whole-paper summaries can use L2 plus L1; broad themes use L3/L2 with scientific L1 evidence; previous reviews use L4; exact experiment questions use structured records; cross-source questions combine records and literature. Memory, metadata, descriptors, necessary native PDF and no-project-evidence cases are represented. FC reconstructs the plan from validated semantic data. The same main conversational agent assesses/refines it and executes existing tools. Paper analysis workers remain available for demanding tasks. The existing corpus SNAPSHOT → PREPARE → MAP → GROUP → REDUCE → VERIFY → ANSWER workflow and one shared corpus planner remain intact.

19. **Side Chat integration.** Removed its separate pre-context reconciliation and routed it through the common gate. The resulting catalog/tree refreshes the visible selection. Existing activity UI displays safe file-checking, evidence, card, topic and readiness stages. The final request carries language policy, compact sync status and bounded evidence. Side Chat's result-producing permissions remain unchanged.

20. **Agent Command integration.** Uses the same context service and shared worker rather than a second implementation. Each invocation gets a fresh turn ID. It waits for synchronization, shares catalog/progress handling and preserves its existing surface-specific authorization for official results.

21. **Recommendation verification.** New tests seed Current Recommendation as `R1` and verify it remains unchanged across additions, deletion, card/topic maintenance and shared context processing. The worker rejects an injected `update_recommendation` capability. Existing tests retain `update_recommendation` as RESULT_PRODUCING, reject it on Side Chat and permit it only through the authorized Agent Command path. The existing renderer tests continue to verify separation between Side Chat and Agent Work state.

22. **FC/Requesty verification.** Provider transport and credentials remain behind FC. The desktop security regression checks renderer/desktop sources for direct Requesty hosts or credentials. Existing authenticated semantic, schema-mapping, native-PDF, mapper and answer route tests remain passing. The implementation adds no local Requesty client. FC sanitization also strips an injected maintenance transcript in the new main-loop integration test. These are local regressions with controlled provider responses; no live provider or deployed FC was exercised.

23. **Unchanged-project benchmark.** Ten unchanged turns over 150 synchronized synthetic sources use the real Electron `ProjectFilesystem` tree/stat adapter and production registry/gate. On macOS arm64, Electron Node 24.18.1, median reconciliation was **4.164 ms** (p95 **5.022 ms**); median main-agent gate time was **4.193 ms** (p95 **5.057 ms**). Every measured turn performed **0 raw source reads, 0 hashes, 0 card calls and 0 QMD updates**. Fixture setup supplies parser/provider/QMD adapters. These measurements exclude semantic/model response latency. Samples and methodology are in [the benchmark artifact](benchmarks/preflight-knowledge-sync.json) and `scripts/benchmark-preflight-sync.mjs`.

24. **Tests and results.** `npm test` passed **345 tests: 55 desktop, 283 FC and 7 local-backend**. The preflight suite contains 12 tests covering unchanged 150-source behavior, add-three/delete-P17, timestamp-only and changed content, legacy cache reuse, Chinese XLSX normalization/deletion/ranking, concurrency/cancellation, L1/L2/L3 failure and resume, both entry surfaces, compact context isolation, language override, layer selection, QMD deletion failure and disappearance during preparation. Existing real QMD integration, Electron renderer, shared corpus planner/cache and security tests also pass. `npm run check`, `npm --prefix alibaba-fc run check`, direct syntax checks for new modules and `git diff --check` passed. After the full run, assertions were strengthened to take scenario B through the existing main-answer loop and check scenario A's no-sync telemetry; the 12-test preflight suite was rerun. Local provider/parser fixtures verify orchestration contracts, not live scientific answer accuracy.
