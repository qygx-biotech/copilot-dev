# Maintained literature wiki (L3)

This adapts the ingest/query/maintenance pattern in [Karpathy's LLM Wiki proposal](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) to the existing local source system. Raw sources (L0), original paper evidence (L1), canonical Paper Cards (L2), topic/wiki knowledge (L3), and historical query-specific reviews (L4) retain their existing roles. The current [evidence-gated maintenance contract](sidechat-literature-maintenance.md) integrates these layers with the direct agent loop.

## Usage

Source synchronization and Paper Card processing integrate new or changed papers into affected topic pages. Existing compatible cards orient the subject; bounded excerpts from original paper chunks support statements. A subject needs at least two papers before it can become a generated cross-paper page. Existing card topics, methods, and entities supply the subjects; overlapping source dependencies supply related-page links.

Use Side Chat with the desired model selected:

- **“Update the literature wiki.”** Builds eligible pages for an existing library or retries pending/stale updates. Compatible unchanged pages are reused.
- **“Explain the thermostability concept.”** Reads relevant pages through the existing saved-artifact tools. It reuses current compatible pages and cards; missing/failed pages alone do not cause a generation call. Pending work originating from a raw-evidence change can receive its first bounded attempt.
- **“Incorporate a thermostability comparison into the literature wiki.”** Explicitly integrates an evidence-backed analysis of the named subject through the same validation and publication path. Requests must name an existing subject; unsupported or ambiguous subject matches do not create arbitrary pages. “Incorporate a thermostability analysis into the wiki” updates matching existing subjects without creating a comparison page.
- **“Check the literature wiki.”** Checks a bounded set of pages without rewriting them or making wiki-generation calls.

The existing selected-paper scope applies. A mixed-source page is excluded when it contains papers outside that scope; it is never silently reduced to a misleading selected-paper summary. Wiki commands do not invoke the L4 review-update workflow. Existing whole-library reviews still use the complete-coverage corpus workflow. Questions about saved reviews still read historical L4 artifacts.

## Storage and compatibility

- `.biodesign/knowledge/topics/index.json` remains the authoritative topic index; `index.md` is a compact navigation projection.
- `.biodesign/knowledge/topics/<id>.md` is the searchable wiki projection.
- `.biodesign/knowledge/wiki_pages/<id>/<key>.json` holds immutable generated revisions, keeping the current and previous successful revision. Their timestamps and links provide a minimal per-page history.
- The cache key includes source hashes, canonical card identities (including their existing source, extraction, schema, prompt, and model compatibility), wiki schema/prompt/excerpt versions, the server's opaque model signature, related-page IDs, and any explicitly incorporated analysis request.

Configuration is refreshed through the existing initiating-turn/model/authentication/workspace-scoped configuration facility. Concurrent wiki tasks with different commands, source scopes, cancellation signals, or models are serialized. Repeated unchanged compatible pages make zero wiki-generation calls and do not rewrite wiki artifacts. Every request performs local reconciliation and currentness checks. Automatic generation eligibility is persisted separately from the configuration-dependent cache key: only initial raw ingestion or substantive contributing raw-evidence changes authorize an attempt. Missing pages, prior failures, restarts and model/prompt changes do not independently authorize spending. Explicit read-only checks remain read-only. Wiki maintenance never regenerates Paper Cards for compatibility or history restoration.

Generation, validation, cancellation, and index-publication failures preserve the previous valid revision. Changed or removed sources invalidate currentness. If fewer than two supporting papers remain, the old revision stays available only as stale historical material. Original citation handles retain their paper/page/chunk provenance; stale handles are not certified against changed originals. Markdown or search-index failure does not prevent reading a committed JSON page through the local fallback.

## Bounds and validation

Each run starts at most eight wiki generations within a five-minute maximum generation budget. The remaining deadline aborts an in-flight provider request; unfinished work stays pending. This is a ceiling, not a delay applied to unchanged requests. Local storage/finalization is separate from provider execution. Each page accepts 2–20 papers, up to 140,000 input characters, and 24,000 characters of Markdown output. Input uses compatible card orientation, the retained page, and up to three subject-ranked original chunks per paper plus chunks needed by retained citations (maximum twelve excerpts per paper). Excerpts are capped at 6,000 characters; an update exceeding bounds stays pending/stale. Original L1 content is neither shortened nor replaced. No full wiki/library upload, new storage service, embedding requirement, or graph database is introduced.

New wiki generation returns natural Markdown: headings, paragraphs, lists and tables have no prescribed sections or statement schema. The model copies complete `[[cite:SOURCE_ID:pPAGE:CHUNK_ID]]` references verbatim from the supplied evidence; the placeholders in this example must never be used as identifiers. Page identity, dependencies, source/card hashes, content hash, configuration and generation accounting live in a host-owned revision envelope, outside the prose. Existing version-one JSON pages remain readable and retain their stricter quoted-evidence validation.

Draft acceptance preserves bounded usable Markdown even with missing, malformed or unresolved citations. Drafts are stored separately and never replace a successful revision. Reference/knowledge validation still blocks publication of such a draft as current knowledge. Before publication or reuse, the host checks current registry identities, reconciled source versions, canonical card identities and original evidence chunks; publication also rechecks physical bytes. Eligible drafts are clearly labeled unverified and their affected passages flagged. Only exact current, in-scope references can become navigation; unresolved/model-authored targets are rendered as inert text. Stale source content is withheld from current answer context, while saved revisions remain available for inspection. Source navigation uses the existing host citation registry and page number. Uncited passages receive visible unverified labels; headings, table headers and open questions need no citation. Cited passages are reference-resolved, not automatically counted as scientifically verified knowledge.

Citation resolution establishes provenance, **not semantic entailment**. Model-reported disagreements are review findings, not guaranteed contradictions. Scientific quality has not been benchmarked. Precise numerical, methodological, and disputed claims still require L1 evidence. Missing or stale wiki coverage requires original retrieval or an explicit limitation. Wiki failures are reported as L3 maintenance failures, including specific validation problems when available, and do not stop a review using valid L2 cards and L1 evidence.

Read-only maintenance checks at most thirty pages for missing artifacts/sources, broken links, stale source/card/generation dependencies, and unsupported references. It flags existing model-assisted disagreement findings for review; it does not run a separate semantic contradiction detector or rewrite unrelated pages. Larger libraries can leave eligible pages pending; later requests can process unattempted pages from the same persisted raw-ingestion event within the bound. Failed attempts require changed raw evidence or an explicit regeneration request.

Answer transport retains the existing maximum of four saved artifacts and 12,000 content characters per artifact, with truncation and currentness metadata. Local lexical subject search supplements existing QMD retrieval and works without QMD or a provider connection. Ordinary questions still run the application's existing source synchronization before wiki recovery or answering. A wiki failure does not abort the direct agent loop, corpus workflow or final answer when valid Paper Cards and original evidence are available. Ordinary Side Chat has no mandatory semantic planner call.

## Pending maintenance and recovery

Each topic in `topics/index.json` has a host-managed `wikiMaintenance` journal. It stores the desired input key, source hashes and card identities, wiki generation configuration, incorporated analysis request, pending/current state, explicit retry cooldowns, bounded failure details and the last four attempts with their source/configuration versions. The existing saved revision and citation format are unchanged. A pending or running journal survives an app restart; an interrupted attempt never counts as a publication.

The separate `wikiEvidence` ledger stores sorted source-ID/raw-hash fingerprints, the originating ingestion/change event, and fingerprints already attempted. Configuration/card identities remain in the audit/cache journal. Both are persisted before generation, including before an outcome could become unknown through cancellation or a restart. Validation and authoritative revision/index publication precede success. A failed generation or publication leaves the previous successful revision available as history. Failed projection/search indexing remains pending and is repaired from the committed JSON without another model request. Stale wiki pages are excluded from current answer context; the maintenance report includes pending reasons, retry times and specific validation problems.

Automatic attempts are deduplicated by page and raw-evidence fingerprint. A failed or interrupted attempted fingerprint cannot retry on an ordinary request, regardless of elapsed cooldown. Unattempted ingestion work deferred by a page/time budget remains eligible. Explicit regeneration can retry, subject to bounded provider cooldown/Retry-After behavior. Configuration changes can invalidate compatibility without authorizing generation. Configuration requests, local reconciliation/projection, cached artifact reuse and actual provider attempts have distinct diagnostics. There is no background retry loop.

Usable incomplete prose is saved under `.biodesign/knowledge/wiki_pages/<id>/<key>-<contentHash>.draft.json`, referenced by `topic.wikiDraft`. `topic.wiki` remains the successful revision. Draft retrieval rechecks current source scope/version and emits sanitized Markdown with explicit unverified labels. Resolving a citation still yields zero automatically verified scientific claims.

## Historical validation evidence

The pre-change shared L3/L4 transport passed all 17 saved-knowledge tests. The previous topic service maintained memberships and placeholder summaries; it made no L3 generation calls.

Synthetic fixtures after this change measure four wiki-generation requests for two papers, zero on an unchanged repeat, and four affected-page requests plus one new Paper Card request when a third related paper is added. A separate unrelated page receives zero update requests. These are logical adapter request counts, not production benchmarks; underlying provider retries may make additional HTTP attempts.

The focused tests cover publication failures, cancellation, incremental dependencies, bounded input/output and maintenance, offline reads, model and workspace isolation, authenticated per-account provider keys, and active-agent consumption with original-paper citations. Existing L4, streaming, history, Agent Command, and Paper Card regressions remain part of the full test suite.

Validation completed: 57 desktop tests, 520 FC/shared frontend tests, and 7 local-backend tests passed (584 total, including 19 focused wiki/provider tests). The full suite passed before the final optional answer-time Paper Card adjustment; the complete FC/shared frontend suite was rerun successfully after that adjustment. `npm run check`, syntax checks for the new modules, and `git diff --check` passed. All provider results in these tests are synthetic; no live-provider or answer-quality benchmark was run.

Earlier recovery-policy verification (superseded by the evidence gate): 797 FC/shared frontend tests and 25 desktop adapter/history tests passed; build and syntax checks passed. The expanded Chinese fixture also repairs failed pages on a later unchanged request, retains all three compatible cards and returns to semantic planning and the corpus workflow. See the [verification report](sidechat-wiki-compatibility-verification.md#request-driven-recovery-extension). No live Requesty rerun was performed.

## Deployment

The current change requires the updated Electron renderer and FC draft-acceptance endpoint/shared contract. Verify `runtimeContracts.wikiDraftAcceptance: 1`; older backends discard citation-invalid draft prose. See [current verification and rollout](sidechat-literature-maintenance.md#verification-and-rollout).

The frontend assets and FC code must be released together for Markdown generation. The existing packaging scripts include the shared contract. No new environment variables are required. A new frontend talking to an older backend reports wiki generation unavailable; that older backend can still reject Gemma planning, so deploying the backend is necessary to repair the reported review failure. See [compatibility verification and deployment](sidechat-wiki-compatibility-verification.md) for the current test results and live runtime checks.
