# Literature maintenance in the direct Side Chat loop

Current Side Chat entry is metadata-only. Maintenance eligibility described below is exercised only after a selected tool requests derived preparation, or through explicit processing. See [demand-driven preparation](sidechat-demand-driven-preparation.md) for tool arguments and call sequences.


This update on `nanobot/sidechat` preserves all existing work and the five layers: L0 raw sources, L1 original evidence, L2 Paper Cards, L3 topic/wiki knowledge and L4 saved corpus syntheses. It supersedes the earlier policy of retrying failed wiki pages on subsequent requests.

## Correctness and generation are separate

Every new request still scans/reconciles the local source catalog and invalidates changed/deleted dependencies. Unchanged compatible evidence and cards are reused. Local reconciliation determines when hashing is needed; wiki cache inspection can reuse the same reconciled source snapshot rather than rehashing each PDF once per topic. Publication checks physical source bytes again. Wiki maintenance never generates Paper Cards merely to restore a page or conversation.

Each topic's existing JSON index entry now has a separate `wikiEvidence` ledger. Its fingerprint hashes the sorted contributing stable source IDs and raw content hashes. It excludes prompt/model configuration, card content, derived prose, paths and related-page metadata. The ledger persists the observed dependencies, ingestion/change eligibility and fingerprints already attempted. The existing `wikiMaintenance` journal retains configuration, source/card identities, failure details and bounded attempt history; attempts also record their raw-evidence fingerprint. Previous saved records load without a schema reset. Old generation attempts migrate conservatively as already attempted; missing records alone do not imply consent to generate.

| Event | Automatic wiki provider call |
| --- | --- |
| Initial raw ingestion or substantive contributing raw-evidence change | Eligible for one bounded attempt per page/evidence version |
| Unattempted ingestion work deferred by the time/page budget | Can use a later request's budget; the authorization remains the original raw change |
| Unchanged question, timestamp-only touch or app restart | No new generation eligibility |
| Prior failed/interrupted attempt or deleted/missing page | No new generation eligibility |
| Model, prompt, extraction configuration or Paper Card content changes | May invalidate compatibility; do not independently authorize wiki generation |
| Explicit wiki update/incorporation request | Separate bounded operation; may retry after applicable provider cooldown |
| Missing searchable projection of a valid committed page | Local repair from saved JSON; zero wiki LLM calls |

Before contacting the provider, the application persists the attempted fingerprint. A crash after that boundary has an unknown outcome, so ordinary replay/restart never resends the request. Jobs deduplicate by page and evidence fingerprint. Attempt details retain the selected configuration even though configuration does not reset the spending gate.

A pass processes eligible pages sequentially with no fixed page-count cutoff, within one five-minute maintenance deadline shared by configuration, admission and generation. In-flight requests receive the remaining deadline and cancellation signal; an uncooperative late response cannot publish after the bounded call has ended. Unfinished work remains pending. The ceiling does not add a wait to unchanged requests. Provider retries remain bounded inside the existing transport; explicit retries and unattempted work respect cooldowns and rate limits. No background retry timer was added.

## Draft prose and current knowledge

The model writes free-form Markdown with flexible headings, paragraphs, lists and tables. It receives no prescribed prose sections or statement JSON. Host metadata remains outside the Markdown. Existing version-one wiki records keep their existing compatibility and validation path.

The FC endpoint accepts a nonempty, bounded Markdown draft even when references fail validation. It returns the prose with `acceptance: unverified_draft`, validation problems, attempt counts and integrity metadata. Empty/oversized content and invalid input/configuration still fail. Provider rejection remains distinct from draft-validation problems.

The host saves usable invalid prose as a separate immutable `.draft.json` record referenced by `topic.wikiDraft`. It contains source dependencies, raw-evidence fingerprint, configuration, content hash, generation details and validation problems. It does not replace `topic.wiki`, the successful published revision. A previous successful revision remains usable when its sources and compatibility are still current, even if an attempted replacement failed. Changed/deleted sources make it historical rather than current.

For retrieval, drafts must still pass current source/version/scope checks. The application renders only references exactly matched to existing current paper IDs, pages and chunks as citation markers eligible for working navigation. Malformed/unresolved markers, model-authored links, URLs and HTML targets become inert text; the original prose stays intact on disk. Passages containing an invalid reference are flagged even if another reference in the same passage resolves. Uncited ordinary passages receive an unverified label; headings and open questions do not require citations.

Drafts are explicitly unverified, not published current knowledge. Citation resolution establishes a reference target, not scientific entailment: integrity metadata always reports `claimVerification: not_semantically_verified` and `verifiedClaimCount: 0`. Validated published wiki prose is also derived interpretation; precise or disputed claims still require original evidence. Publication requires validation and committed revision/index state. Source failures or failed publication cannot replace the previous successful revision.

## Tools, history and diagnostics

`search_project_knowledge` now exposes bounded current compatible Paper Cards along with eligible wiki pages/drafts and historical syntheses. Card identities, raw hashes and generation metadata accompany the results. This is local cached retrieval, with no card/wiki regeneration. `retrieve_project_evidence` supplies original passages when summaries omit details. `run_corpus_workflow` continues to reuse the existing cards/maps and measure whole-corpus coverage.

The hard source scope is enforced in the host, including an empty/deleted selection. Wiki pages that depend on excluded papers are withheld rather than silently rewritten to fit the selection. Tool results and saved prose remain untrusted data. Existing transcript pairing, historical replay, stable identities, bounded compaction, source-file protections and recommendation-write protections are unchanged.

Diagnostics separately identify local reconciliation, cached card reuse, wiki generation/skips, local wiki maintenance time, provider generation time, image processing, model-selected tool execution and historical replay. Configuration requests are not inference calls. A pending failed wiki remains partial maintenance; `evidence_already_attempted` explains the skipped call and does not imply a scheduled automatic retry. Offline/unconfigured generation is reported separately from successful source synchronization. A skipped call is not counted as a successfully updated page.

## Automatic page admission (2026-09-24)

All Wiki page creation has a host-owned ceiling, including explicit updates and incorporation requests. After the existing reconciliation, N is the unique count of project registry paper sources, excluding missing/removed/deleted records. Paper Card success is irrelevant to this count. The ceiling is zero for N < 2, otherwise `min(30, max(3, ceil(N / 4)))`. This is an upper bound, not a desired page count. The project-wide count does not change the existing hard selection: only candidate pages whose contributing papers are all permitted can be generated.

Each topic can carry optional `wikiAdmission: { schemaVersion: 1, origin, admittedAt, key }` metadata in the existing `.biodesign/knowledge/topics/index.json`. Origins are `automatic`, `explicit`, and `legacy`. Admission is independent of `wikiEvidence` and its eligibility/attempt fingerprints. Reservations are persisted before provider work, serialized by the existing maintenance queue, and retained after failure, cancellation or restart. A failed reservation write aborts maintenance before generation and rolls back the in-memory reservation. The empty-topic pruning path preserves reserved/pending pages.

The count is a union by page ID: a published page, saved draft, persisted generation attempt, and reservation on one topic occupy one slot. A label or preparation-only maintenance record does not itself reserve a slot. Existing saved published/draft/pending topics are grandfathered without modifying their prose or replacing revision pointers. They continue to count when stale or failed; lowering the ceiling does not delete or release them. Projects already above the ceiling can update their existing eligible pages but admit no additional pages. Explicit update/incorporation operations cannot exceed the ceiling. Refreshing an eligible existing page uses its existing slot.

Lightweight topic/index nodes remain available without admission. Every candidate, including an existing page refresh, needs 2–20 distinct current original-evidence-capable contributors. Before a new slot is reserved, the production source checks and input builder verify physical source bytes, compatible cards, evidence provenance and full input bounds. Local ranking prioritizes existing pages/reservations, then concepts/methods/comparisons, entities, and generic parent nodes; within each class it prefers more current supporting papers and breaks ties by stable topic ID. Candidate labels use conservative Unicode/case/whitespace/internal-hyphen normalization to avoid duplicate orthographic aliases. Chemical charge punctuation is retained, and comparisons use a distinct key. Existing matching pages win over new aliases. Scientific topics are not merged merely because their contributing papers overlap. This admission heuristic does not claim scientific equivalence or semantic quality, and adds no provider/classifier/subagent call.

Admission never sets a raw-evidence eligibility fingerprint. The existing observation policy still records initial ingestion or substantive contributing-source changes, including for deferred topics, before admission decisions. A reserved missing page with no eligible raw change cannot generate. Prompt/model changes, restarts, previously failed attempts and unchanged requests do not authorize a call. Unattempted work already authorized by ingestion can still proceed under the existing budget/cooldown policy. The five-minute maximum, source hashes, compatible-card reuse, publication validation and previous-revision preservation remain. The former three-page per-run cutoff is removed; see [the current scheduling contract](wiki-admission-scheduling.md).

Maintenance returns `admission` with `topicCandidateCount`, `projectPaperCount`, `automaticPageCeiling`, `existingReservedPageCount` **before** admission, `admittedCandidateCount` for new slots, `totalReservedPageCount` **after** admission, remaining headroom, and separate rejected/deferred counts. The legacy field name `automaticPageCeiling` now applies equally to explicit updates. Per-page results report eligibility, reason/code, duration and known/unknown provider attempts; overall results include updated/reused/rejected/failed/deferred counts, pending work, deadline status and `automaticRetryScheduled: false`. Safe logger events include `wiki.candidate-admission`, `wiki.page-stage`, `wiki.page-outcome` and `wiki.maintenance-outcome`. No prompts, evidence, raw outputs or credentials are logged.

## Local deadline recovery

The only new automatic retry authorization is a persisted `retryable_timeout` from the local Wiki generation deadline. The raw-evidence fingerprint remains consumed; the journal explicitly permits recovery of that fingerprint. Other provider/transport, content, provenance or publication failures keep their existing regeneration policy. User cancellation revokes timeout recovery. Legacy interrupted attempts are not guessed to be timeouts.

Each admitted page stores timeout recovery alongside its existing attempt journal in the topic index: evidence fingerprint, source dependencies, actual configuration, cumulative timeout count and next eligible time. Attempts record generation duration, desktop transport start, known/unknown provider start and completion, and scheduling sequence/class. Local abort leaves remote completion **unknown**: it is not proof that the provider stopped. A late response cannot publish after the local deadline. A valid already-published matching revision is reused and its projection repaired locally before considering another request. Changed evidence supersedes the old timeout ledger; changing model/prompt alone grants no generation authorization. An authorized timeout retry uses the currently selected model and records that configuration.

Cooldowns after consecutive timeouts for the evidence version are **1 minute, 5 minutes, 15 minutes, then 60 minutes** for every subsequent timeout. The cumulative count survives the bounded four-entry attempt history. Cooldown expiry does not launch work: a later maintenance request or explicit operation is required. Restart preserves cooldowns and history, with no lifetime timeout-retry cutoff.

A run makes at most one logical generation request per eligible page, with **no fixed per-run page-count cutoff**, within the original **five-minute maintenance deadline**. The existing queue and page/fingerprint job deduplication serialize concurrent requests. Fresh eligible pages and due timeout retries alternate, oldest attempted sequence first with stable page-ID ties; after a deadline-consuming fresh attempt, fresh work gets the next slot. This prevents one slow topic from monopolizing later requests. Local reuse/projection repair does not spend a generation slot.

Scheduling uses the maximum observed generation duration for that page and selected model (otherwise other pages using that model), multiplied by 1.25 and bounded to 60–240 seconds. Without observations the conservative estimate is **90 seconds**. The 240-second cap lets a page start in a fresh five-minute run. If insufficient time remains, work is deferred without a provider request or fingerprint consumption, including when journal persistence consumes the remaining time. A request still queued in the client’s shared provider cooldown is also deferred without consuming evidence; it is not an in-flight generation timeout. Estimates never extend the deadline or switch models.

The desktop Wiki adapter sends once; Function Compute retains its existing maximum of **two provider attempts** for a logical generation. Generation and its optional single targeted model repair share those two attempts; desktop resends do not multiply them. Cancellation/time budgets still apply. Safe `wiki.attempt-outcome` diagnostics distinguish deferred work, cooling down, retryable timeout, validation/generation failure and publication, recording counts/times and provider outcome without content or credentials. Partial maintenance still allows answers from valid Cards and original evidence after maintenance returns. Maintenance remains foreground work awaited by the initiating conversation, so its elapsed time adds to conversation latency. No background scheduler is introduced.

The scheduling change affects host maintenance/client behavior and removes the shared per-run generation-count ceiling. It requires rebuilt/reloaded desktop assets to activate; it does not introduce a backend API change or require a Function Compute deployment by itself. No deployment or running-app restart/reload was performed. Tests use fixture provider responses and accelerated host deadline callbacks, not live Requesty inference.
